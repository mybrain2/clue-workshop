# 线索研判看板：开源调研与拼装设计

调研日期：2026-09-01

## 结论先行

没有找到一个成熟开源项目能同时覆盖“案件背景与初始线索录入、账号/联系方式/IP/设备/群聊多跳关系、内部授权数据查询编排、人工核验、待查提示、可审计结论和结构图”。最接近的正确路线不是强行改一个大而全平台，而是：

- 以 **Flowsint** 的图谱调查交互作为可二开代码基线；
- 以 **Casebook** 的案件、证据、假设、时间线、不可变事件思想作为工作流参考；
- 以 **POLE** 为实体关系模型起点，并扩展账号、联系方式、登录事件、社交群和设备；
- 以 **sift-kg** 或 Neo4j LLM Graph Builder 的“材料 → 候选实体/关系 → 人工确认”管线处理笔录、聊天、Excel、报告等非结构化材料；
- 由自建的“授权数据源适配器 + 规则型调查清单 + 报告生成器”补齐真正的业务能力。

不建议把 OpenCTI、Aleph、SpiderFoot、GraphRAG 或 CrimeSys 当作系统底座。它们可分别借鉴溯源、资料检索、模块化、抽取和 POLE 演示，但都不满足案件级权限、人工确认和业务数据模型要求。

## 候选项目分层

### A. 建议进入 PoC 的代码或实现参考

1. **Flowsint**  
   - 仓库：<https://github.com/oblonka/flowsint>  
   - 定位：Neo4j 驱动的调查图谱工作区，支持实体关系探索与可扩展 enrichment。2026 年仍有提交；Apache-2.0。  
   - 可复用：关系图交互、实体详情面板、图谱探索、enricher 的插件化边界、Docker 化部署。  
   - 缺口：仍属早期项目；没有案件授权数据模型、证据链、字段级权限和适合中文账号关系的本体。  
   - 判断：**最适合做前端图谱体验和扩展器框架的代码基线，但不能原样上线。**

2. **Casebook**  
   - 仓库：<https://github.com/Ashborn-047/Casebook>  
   - 定位：本地优先的事件溯源案件与证据管理；支持自动/手工连线、假设、时间线、SHA-256 完整性、审计与 PDF/JSON 导出。MIT；2026 年仍有提交。  
   - 可复用：案件工作区结构、证据与假设的分层、关系边必须写“为什么相关”、事件溯源、报告布局。  
   - 缺口：主要存储在浏览器 IndexedDB；可选远程同步并不能替代服务端案件授权、内部数据源调用和完整图数据库。  
   - 判断：**适合借鉴/选择性复用 UI 与事件模型，不建议原样作为多用户案件底座。**

3. **sift-kg**  
   - 仓库：<https://github.com/Exios66/dox-knowledge-graphs>  
   - 定位：PDF、文本、HTML 到知识图谱的本地 CLI；支持自定义实体/关系类型、来源段落回溯、候选去重人工批准、关系低置信审查、交互图和叙事报告。MIT。  
   - 可复用：`LLM 提名 → 人工确认/拒绝 → 写入图谱` 的闭环，尤其适合材料导入时自动发现账号、电话、时间和候选关系。  
   - 缺口：CLI/文件批处理产品，不是多用户案件应用；其默认 OSINT schema 也不等于你的内部数据模型。  
   - 判断：**优先作为“材料自动抽取与候选关系生成”组件参考。**

4. **Neo4j POLE 示例**  
   - 仓库：<https://github.com/neo4j-graph-examples/pole>  
   - 定位：Person、Object、Location、Event 的犯罪调查图谱样例。  
   - 可复用：用“人、物、地点、事件”而不是一堆扁平字段组织案情；适合定义关系查询和图谱索引。  
   - 缺口：它是示例数据/Schema，不是应用；示例依赖的旧 Neo4j 版本不应直接照搬。  
   - 判断：**模型起点，不是代码底座。**

### B. 只借鉴局部思想，不作为底座

- **DFIR-IRIS**：<https://github.com/dfir-iris/iris-web>。案件、任务、时间线、API、报告与协作较完整，但主要是安全事件响应，许可证 LGPL-3.0；可参考“案件模板与任务闭环”，不宜硬改成账号社交关系平台。
- **OpenCTI**：<https://github.com/OpenCTI-Platform/opencti>。可参考来源溯源、置信度、时间有效性、连接器和分析对象关系；STIX/威胁情报本体与本案需求差异大，部署重，不能直接承载案件事实库。
- **Neo4j LLM Graph Builder**：<https://github.com/neo4j-labs/llm-graph-builder>。值得参考文档分块、schema 引导抽取、全文/向量/图检索和实体合并；使用前须独立核验许可证、依赖和维护状态。
- **Microsoft GraphRAG**：<https://github.com/microsoft/graphrag>。可做材料摘要、候选关系发现和问答辅助；官方明确为维护模式的研究示例，不宜做事实库或图形工作台。
- **IntelOwl**：<https://github.com/intelowlproject/IntelOwl>。借鉴 Playbook、Analyzer 和 Pivot 编排思想即可；不要把安全情报结果或自动扩展结果当案件事实。

### C. 明确不选

- **Aleph**：<https://github.com/alephdata/aleph>。文档与结构化资料检索能力强，但维护已于 2025-12-31 结束，不能作为新项目基础。
- **CrimeSys**：<https://github.com/DeerajKarthik/CrimeSys>。POLE + Neo4j + LLM-to-Cypher 演示明确，但仓库仅少量文件、2025 年单次提交级别，缺权限、审计与查询安全；仅供原型参考。
- **SpiderFoot**：<https://github.com/smicallef/spiderfoot>。仅可作为隔离环境中的、经授权的公开信息核验辅助工具。其含主动扫描/枚举能力，外部数据质量和服务条款不可控，不可作为案件核心依赖或自动扩线索入口。

## Hugging Face 与模型层结论

Hugging Face 上没有可直接替代案件工作台的成熟产品，价值在于“材料抽取助手”，不是事实判定器。

- **GLiNER multilingual v2.1**：<https://huggingface.co/urchade/gliner_multi-v2.1>，Apache-2.0。可在本地用自定义标签识别“姓名、QQ、微信号、手机号、IP、设备标识、平台账号、群聊、地点、时间、案号”。适合作为初筛候选生成器。
- **mREBEL**：<https://huggingface.co/Babelscape/mrebel-large>，可做多语言关系三元组抽取，但页面许可证文字/链接存在不一致，且通用关系模型未针对中文办案材料评测，**不建议纳入首版依赖**。

模型输出一律只能写入“候选实体/候选关系”，不能自动覆盖人工建立的事实关系；每一条候选必须保留原文片段、来源文件、页码/行号、模型版本、置信度和审核状态。

## 建议的案件专用模型

### 1. 不直接把“账号相同”写成“人相同”

核心对象分四层：

```text
案件 Case
  └─ 证据/数据来源 SourceArtifact
       └─ 观察记录 Observation（不可变：某来源在某时观察到什么）
            └─ 候选实体/候选关系 Candidate
                 └─ 已核验实体/已核验关系 Confirmed Graph
```

因此，手机号关联多个 QQ、微信或平台账号时，先建立多个 `Account` 节点与带来源的 `BOUND_TO_PHONE` 观察关系；只有具备足够证据并经分析人员确认后，才把账号归并到同一 `Person` 或“待识别主体”。这样能避免手机号复用、账号转让、同名与共享设备造成误认。

### 2. POLE 的本案扩展

建议第一版支持以下实体：

- `Person / UnidentifiedSubject`：已识别人员或待识别主体
- `Account`：QQ、微信、手机号、平台账号，包含类型、原始值、规范化值、别名与状态
- `Device`：设备指纹、终端标识、SIM/IMEI 等已获授权字段
- `NetworkEndpoint`：IP、网络段、归属地/位置描述
- `Group`：群聊、好友圈、频道、共同活动集合
- `Organization`：公司、工作室、团伙候选、平台主体
- `Location`：居住/登录/出现地点，区分精度与来源
- `Event`：登录、加好友、入群、转账、发布、通话、材料记载等
- `Evidence / Document / DataBatch`：原始文件、内部查询批次、笔录、截图、表格
- `Case / Task / Hypothesis / Finding`：案件工作流对象

关键不是只存边名，而是每条关系都带：`source_id`、原始定位、观察/发生时间、导入批次、数据权限、置信度、审核状态、创建人和版本。

尤其“同机登录”“同 IP”“同群”“共同联系人”应通过中间事件表达：

```text
账号 ─参与→ 登录事件 ←使用─ 设备
登录事件 ─发生于→ IP/地点
账号 ─成员→ 群聊
```

系统可以据此生成“共用设备候选”“同网段共现候选”，但不得直接把它渲染成“同一人”或“团伙成员”的结论。

## 交互：你要的“选关系直接填”应这样做

创建案件先只填写：案件背景、调查范围/授权、初始线索、已知来源。随后以实体抽屉进行录入：

1. 选择实体类型，例如“QQ 账号”。
2. 填账号值、别名、来源、时间范围；系统先规范化与查重。
3. 点击“新增关联”，选择如“绑定手机号 / 使用设备 / 入群 / 同机登录 / 好友 / 同 IP 出现 / 公开平台账号”。
4. 为关系填写来源、原始定位、时间、确定性与说明；低证据关系默认标为“待核验”。
5. 图谱立即刷新，同时生成可追溯的事件日志。

不做自由画线的“毛线团”。线必须有类型、来源和时间；每条线点开都能回到数据批次、文件页码或内部查询记录。

## “还要查什么”的实现方式

首版不让大模型自由建议，而以可审计的规则清单驱动。每条建议都必须说明触发原因和需要的数据权限。

示例：

- 新增 QQ/微信/平台账号但无来源：提示补录来源与观察时间。
- 已有手机号但没有对应账号核验：生成“在已授权内部库查询手机号关联账号”的待办。
- 账号出现登录 IP 但无设备记录：生成“核验同一时间窗内设备/终端标识”的待办。
- 一台设备关联多个账号：提示按时间窗检查账号是否共现；结论仍为“共设备候选”。
- 群聊出现多个种子账号：提示统计共同群、直接好友、共同设备与共同联系方式，生成候选社交簇。
- 同一联系方式在不同公开平台出现：提示人工比对昵称、时间、头像/内容等可公开验证特征，避免仅凭号码归并。
- 图内高权重节点或跨案件重复实体：提示检查是否存在未处理别名、重复记录或跨案关联授权。
- 关系无原始来源、置信度低或互相冲突：进入“待审核关系”队列，而不是加入结论。

每一个待办可绑定案件、实体、数据源范围、执行人、审阅人和完成依据，形成真正能执行的调查清单。

## 报告与结构图的正确输出

报告不应由模型直接写“某人就是团伙成员”。它应固定分为一条连贯主线：

1. 案件背景与调查范围；
2. 初始线索及其来源；
3. 已核验的实体、账号和联系方式关系；
4. 关键时间线与直接证据；
5. 需要谨慎表述的候选关联及其依据/反证；
6. 当前关系结构图（可按时间、关系类型、审核状态过滤）；
7. 尚未完成、但已具备明确输入和授权范围的调查事项。

每个关键结论自动附“依据来源、观察时间、审核状态”。报告中的“事实”“候选线索”“待调查问题”必须视觉和语义分层，防止把算法关联混入事实认定。

## 推荐技术组合

不建议拼一个无法维护的“大杂烩”。建议在统一数据模型下只保留三类可替换组件：

```text
React + TypeScript + Cytoscape.js/Flowsint 图谱能力
                    ↓
FastAPI 或 NestJS：案件、任务、审核、报告、授权数据源适配器
                    ↓
PostgreSQL：案件/权限/任务/审计/版本
Neo4j：实体、事件、多跳关系与图查询
对象存储：原始材料和导入批次
```

- `PostgreSQL` 不是替代 Neo4j，而是承载权限、工作流和审计等事务数据。
- `Neo4j` 只保存经授权的图谱视图与可追溯引用；原始数据保留在来源/证据层。
- `Source Adapter` 只接入已授权的内部数据与合规公开信息；外部查询必须经过白名单、用途声明、限流与审计。
- 文档抽取可离线/内网运行，先用规则（手机号/IP/账号格式）和 GLiNER 召回，再由 LLM 做受控关系提名。

## 分阶段实施建议

### P0：单案可用看板

目标：让办案人员不再在 Excel、截图和脑内记忆之间手工拼图。

- 新建案件、背景/初始线索录入；
- 10 类核心实体和关系表单；
- Excel/CSV 批量导入；
- 关系图、实体详情、来源回溯、时间线；
- 规则型“待查清单”；
- Markdown/PDF 调查摘要草稿；
- 导入、编辑、审核、导出的全量审计。

验收标准：给一份含账号、手机号、IP、群关系与设备关联的脱敏样本，10 分钟内完成入图；任一关键结论可在两次点击内回到具体来源。

### P1：内部数据适配与多人协作

- 按数据所有权接入内部授权查询适配器；
- 案件/字段级权限、数据密级、敏感字段脱敏；
- 任务派发、双人审核、证据/关系版本；
- 相同号码、账号别名、同设备/同 IP 的候选聚合与冲突提醒；
- 可配置调查 Playbook。

### P2：材料智能处理与研判辅助

- 文档、笔录、聊天和截图 OCR 的候选抽取；
- 实体消歧人工审核队列；
- 基于已确认关系的社交簇、时间窗、共同标识分析；
- 只基于已确认/可回溯材料的问答和报告辅助。

## 必须从第一天做的边界

- 仅在已有合法授权和案件用途范围内接入、查询和扩展数据。
- “来源记录”“候选线索”“人工核验事实”“报告结论”必须分层，不可被模型或自动规则直接跨级。
- 不把公开平台检索、外部接口查询或自动化扫描默认为无风险；查询本身要记录用途、操作者、字段与时间。
- 以服务端案件授权为边界，不能依赖前端隐藏或仅按组织筛选。
- 不让 LLM 生成任意 Cypher 直接访问生产图数据库；自然语言查询必须转换为受限模板、参数化查询，并返回证据引用。

## 建议的下一步

先不要上来就接内部数据源。最稳的是先用脱敏样本完成一个 P0：确定实体/关系字典、导入格式、图谱交互和报告结构。P0 跑过 2—3 类真实案件样本后，再决定直接二开 Flowsint，还是只借其图谱交互而自建 React 前端。这样能先把“办案人员真正怎么填、什么提示有用、什么线会误导”固化下来，避免先造一个漂亮但不适合你们数据口径的图谱壳子。
