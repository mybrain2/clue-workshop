# 复杂账号画像：成熟开源底座与产品重构

## 结论

前面的“线索树”只解决了**怎么读**，没有解决你真正的数据形态：

```text
一个账号 → 多个手机号
一个手机号 → 多个 QQ / 微信 / 平台账号
一个 IP / 设备 → 多个账号
一个群聊 → 多个主体
一个主体 → 多个群聊 / 账号 / 团伙
多个路径又会回到同一账号或同一群聊
```

这不是树，是一个会不断分叉、合流、回连的**多主体关系网络**。

因此产品必须同时有两层：

1. **底层：关系图**，允许任何节点与多个节点相连；
2. **上层：线索树**，从当前初始线索出发，把关系图按“我正在查的这条路”折叠成易读脑图。

XMind 式视图是默认阅读模式，不是底层数据结构。

## 成熟开源项目与组件：重新排序

### 1. G6：主画布，推荐作为核心图形底座

- 仓库：<https://github.com/antvis/G6>
- 许可证：MIT
- 特点：成熟图可视化引擎，节点、关系边、Combo（分组/聚合容器）、多布局、交互、React 节点、Canvas/SVG/WebGL 渲染均有支持。
- 适合本项目的点：
  - 用一份图数据同时切换“线索树”“关系网”“聚合总览”；
  - 将“同 IP 账号（28）”“群成员（63）”“共同设备账号（12）”显示为可展开聚合节点；
  - 用不同视觉强度区分账号链、登录关系、群聊关系、平台关系；
  - 允许点击节点后只展开一跳或两跳，避免毛线团；
  - React 节点可以做成真正可读的账号卡、群聊卡、折叠统计卡，而不只是圆点。
- 取舍：树形布局、Combo 折叠和大图性能必须以真实案件脱敏样本做 PoC；但它是目前最适合统一承载三种视图的候选。

**结论：G6 应作为第一选择。**

### 2. Mind Elixir：只做“线索脑图”视图或导出，不做主图

- 仓库：<https://github.com/SSShooter/mind-elixir-core>
- 定位：成熟思维导图核心，支持折叠展开、节点编辑、拖拽、撤销重做、JSON/HTML/XMind 导出及 React 生态。
- 可用之处：
  - 把当前案件的一条调查路径变成真正接近 XMind 的阅读/汇报脑图；
  - 展示“某微信 → 某手机号 → 多个 QQ → 各自群聊”的当前展开路径；
  - 支持导出图片或 XMind 文件做汇报。
- 不能承担的部分：
  - 一个 QQ 同时属于手机号、IP、设备、群聊等多个父级时，树不是天然表达；
  - 不适合处理高密度群聊网络、共同 IP、同设备等交叉关系。

**结论：作为“脑图模式/导出模式”的增强组件，不能替代 G6。**

### 3. Cytoscape.js：关系网模式的备选，不作为第一版双引擎

- 官网：<https://js.cytoscape.org/>
- 许可证：MIT
- 特点：长期维护的关系网络库，适合社交网络、图论算法、局部关系网、选择/过滤/高亮。
- 适合：群聊成员、多账号共 IP、同机账号、共同群等高交叉网络的“局部关系网”视图。
- 不作为第一版首选的原因：
  - 它很强，但更偏网络分析工具气质；
  - 若 G6 已能满足树、聚合和关系网，双引擎会造成交互和样式不一致；
  - 折叠、聚合、业务语义仍需自建。

**结论：若 G6 在真实高密度群聊图上性能或布局不达标，再引入 Cytoscape.js 做独立的“关系网分析模式”。**

### 4. React Flow：不作为主画布

- 仓库：<https://github.com/xyflow/xyflow>
- 许可证：MIT
- 特点：成熟 React 节点/边编辑库，维护活跃、定制能力强。
- 不选作核心的原因：它天然偏“流程图 / 工作流编辑器”。会诱导用户手工拉线、排图，而本产品的原则是系统自动建关系、自动排版，用户不画图。

**结论：不用于案件图主画布。可借鉴其 React 节点和局部交互经验，但不进入实现清单。**

### 5. Casebook / Flowsint：不 fork，只借产品结构

- Casebook：<https://github.com/Ashborn-047/Casebook>，MIT；可借案件工作区、关系说明和导出思路。
- Flowsint：<https://github.com/oblonka/flowsint>，Apache-2.0；可借局部关系探索、图谱详情和节点展开体验。

它们的问题相同：前者偏案件/证据管理，后者偏通用 OSINT 图谱，均不等于“极少点击的复杂账号画像录入器”。直接 fork 会被它们既有页面和模型拖着走。

**结论：不要拿它们当底座，最多借交互细节和代码结构。**

## 产品模型：不是“人”，先是“主体簇”

系统初始不应该要求你判断“这是不是同一个人”。

### 节点类型

```text
主体簇 Subject Cluster：一个正在追的未知主体、团伙候选或案件分支
账号 Account：QQ、微信、平台账号
联系方式 Contact：手机号
网络与设备 Endpoint：IP、设备
社交容器 Social Container：好友集合、群聊、频道
组织 Organization：团伙、工作室、平台主体
```

其中最关键的是：`主体簇`不是实名人员，而是一个人为建立的工作容器。

例如：

```text
主体 A（从微信 wxid_1 起）
主体 B（从群 8899 内的账号 q_222 起）
```

当两边后来通过同一个手机号、设备或群聊相连，系统显示“主体 A ↔ 主体 B 存在交叉”，由你决定是否合并，不能自动当成同一人。

### 关系类型

```text
账号 ─关联→ 手机号
手机号 ─关联→ 账号
账号 ─登录于→ IP
账号 ─同机于→ 设备
账号 ─成员→ 群聊
账号 ─好友→ 账号
账号 ─公开平台账号→ 平台账号
账号/群聊 ─关联→ 团伙
```

一切关系允许一对多、多对多和回连。

## 正确的界面：不是“左侧录入、中间画图、右侧摘要”的三栏静态页面

真正适合你的是一个**调查画布**，每个节点都像一张可展开的卡片。

### 节点卡片的三个层级

以 `微信 wxid_xxx` 为例：

```text
┌─────────────────────────────┐
│ 微信 wxid_xxx                │
│ 已关联：手机号 2 · QQ 5 · 群 3 │
│                             │
│ [+ 手机号] [+ QQ] [+ IP]     │
│ [+ 同机] [+ 好友] [+ 群聊]   │
│ [展开全部]                   │
└─────────────────────────────┘
```

- **摘要层**：只显示各类关联数量；
- **展开层**：点击 `手机号 2` 才出现具体号码；
- **编辑层**：点 `+ QQ` 后只出现一个可粘贴输入框，回车即保存。

这解决“一查出很多手机号 / QQ”的情况：默认只看到数量，想看哪一枝才打开哪一枝。

### 批量结果不拆成多次操作

用户查询一个手机号发现 9 个 QQ，操作应该是：

```text
当前节点：手机号 13800138000
添加：关联 QQ

[粘贴 9 个 QQ，每行一个]

[添加 9 个账号]
```

保存后，手机号卡从：

```text
关联 QQ：0
```

变成：

```text
关联 QQ：9  [展开]
```

而不是生成 9 个满屏节点。

### 群聊必须是“可分叉的关系中心”

群聊不是备注，也不是某个账号的附属字段，而是一等节点：

```text
群 8899
├─ 成员账号（56）
├─ 已建立主体（4）
├─ 共同设备（2）
├─ 共同 IP（5）
└─ 关联群聊（3）
```

- 默认把成员折叠成统计枝；
- 点击成员枝，只展开当前需要看的账号；
- 群内账号可以各自长成主体簇；
- 若群内两个账号已在其他路径中存在，显示为引用/回连，不复制一个新节点。

## 三种视图，一份数据

### 1. 调查路径（默认）

用途：边查边填，沿着当前节点往外走。

- 以当前初始线索或主体簇为根；
- 只看当前展开分支；
- 大分支以“QQ（9）”“群成员（56）”折叠；
- 支持一键切换当前根节点；
- 是最接近 XMind 的模式。

### 2. 主体关系网

用途：看交叉、共同 IP、共同设备、共同群、跨主体回连。

- 节点显示为账号、手机、IP、设备、群聊和主体簇；
- 可以只看一跳/两跳；
- 支持按关系类型筛选：只看“同机”、只看“群聊”、只看“手机号链”；
- 高连接节点自动收成聚合卡，例如“同 IP 账号（37）”。

### 3. 自动全量表

用途：导出、复核和快速检索。

| 主体簇 | 当前对象 | 关系 | 关联对象 | 关联数量 | 展开状态 |
|---|---|---|---|---:|---|
| 主体 A | 微信 wxid_xxx | 关联手机号 | 13800138000 | 1 | 已展开 |
| 主体 A | 手机号 13800138000 | 关联 QQ | QQ（9） | 9 | 折叠 |
| 主体 A | QQ 123 | 成员 | 群 8899 | 1 | 已展开 |
| 主体 B | 群 8899 | 成员 | 账号（56） | 56 | 折叠 |

表由图自动生成，不再要求用户维护。

## 自动简报：生成“可调查结构”，不是流水账

系统应输出四段：

1. **起点与主链**：从哪个账号/手机号/群聊开始，当前已延展到哪里；
2. **账号画像**：每个主体簇内的 QQ、微信、手机号、IP、设备、平台账号数量及主要交叉节点；
3. **社交扩展**：群聊、好友、共同 IP、共同设备带出的其他主体簇；
4. **下一枝**：当前哪些高价值分支尚未展开，例如“手机号 138... 已关联 9 个 QQ，其中 7 个尚未展开群聊关系”。

它不是说“请你做任务”，而是把当前网络的未展开分支按价值排出来。

## 设计方向：不做黑客面板，不做土味大屏，不做泛企业仪表盘

设计应采用：**编辑式调查案卷 + 高密度画布**。

### 视觉语言

- 主色：纸张白、烟灰、墨蓝；账号、手机号、IP、设备、群聊用低饱和色区分；
- 字体：正文清晰、数字等宽；不使用赛博蓝紫渐变、发光边框或大面积玻璃拟态；
- 节点：像精致的索引卡或案卷标签，而不是圆形气泡；
- 关系：主链清晰实线，跨主体回连为弱化曲线；
- 动效：只在展开/收起、局部聚焦和模式切换出现，时长短，不做炫技；
- 留白：画布大，外围控制栏克制，信息靠层级和筛选而非卡片堆叠。

## Skill 结论

### 已有最适合的设计 Skill：Impeccable

- 项目：<https://github.com/pbakaus/impeccable>
- 许可证：Apache-2.0
- 价值：它不是图谱组件，而是防止产品长成“通用 AI 管理后台”的设计约束。
- 对本产品最有用的规则：
  - 渐进式披露，不让用户第一次看到全部字段；
  - 高信息密度但不套一层层卡片；
  - 拒绝默认紫蓝渐变、毛玻璃、霓虹与仪表盘模板；
  - 用有意图的版式、排版和局部状态动画，让调查画布保持克制且可读。

### 市场搜索结果

SkillHub 没有检索到一个足够成熟、专门针对“调查图谱 / 思维导图 / 关系工作台”的设计 Skill；返回结果大多无关或相关度过低，不值得为了“有 Skill”而安装。

因此不安装陌生 Skill，直接以 `Impeccable + G6 官方文档 + 真实案件样本 PoC` 为设计和实现标准更可靠。

## 推荐的最终组合

```text
产品交互与视觉约束：Impeccable Skill
主要画布：AntV G6 v5
脑图导出/独立阅读模式：Mind Elixir
关系网高密度模式：先用 G6；若 PoC 不足再引入 Cytoscape.js
案件与关系数据：PostgreSQL（第一版即可）
前端：React + TypeScript
```

不要直接 fork 调查类开源项目。它们会让产品走回“专业工具功能堆叠”的老路。

正确方式是：用成熟图形引擎承接复杂网络，用你自己的“当前节点下一枝 + 批量粘贴 + 聚合折叠 + 自动简报”来决定产品体验。
