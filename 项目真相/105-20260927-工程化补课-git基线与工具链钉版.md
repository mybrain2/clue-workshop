## 业界标准参照（调研结论）

三层工具链：
1. **交叉编译静态检查**：`cargo check --target x86_64-pc-windows-gnu`（已做）；进阶是 [cargo-xwin](https://github.com/konstin/cargo-xwin)（交叉编译到真 msvc target，需下载 Windows SDK ~500MB）
2. **CI 真机构建**（业界主流）：[tauri-apps/tauri-action](https://github.com/tauri-apps/tauri-action) 官方 GitHub Action，windows-latest runner 上构建 NSIS + 自动算哈希传 Release
3. **本地 VM**（开源方案）：[qwin](https://github.com/pi0/qwin)（QEMU 装 Windows Server 评估版，Apple Silicon 可跑，cargo-xwin 编译后 SCP 进 VM 冒烟，全循环约 5 分钟）；Wine 不适用 Tauri（无 WebView2）

验收漏斗：L0 静态检查 → L1 单元测试 → L2 二进制冒烟 → L3 安装冒烟 → L4 GUI 冒烟。旧交接包只覆盖 L0（弱版）+ L4 清单。

## 经验沉淀

1. `.gitignore` 规则锚定是高危区：嵌套目录（app/src-tauri/）下的 target 用 `**/target/`，写完必须 `git check-ignore -v` + `git ls-files` 分布抽查验证——本条从 13 万文件差点入库的实战中来
2. 双副本文档（项目内 release/windows/ vs 桌面交接包 文档/）必须明确**单一事实源方向**：本轮确立"项目内为主副本、打包时同步到桌面"，旧教训是两边各自演化出 0.7.14/0.7.15 两个版本
3. 锁文件存在就应配 `npm ci`，"带了锁文件却用 npm install"等于锁了但没用上
4. 交接包带 SHA256 清单应是默认纪律，与 macOS 发布包对齐
